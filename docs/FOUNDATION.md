# Phase 3前の基盤整備 — v0.2.0

2026-11-01。Phase 2の交易ルール、固定相場、船・航路定義は維持。

## 表示

presentation/locales/ja.json と en.json にCLIの文字列・名称・エラーを分離。
通貨略記はCr。プレイヤー別言語をpreferencesに保存し、--langは一時的上書き。
既存DTOの日本語nameは互換維持し、表示側だけで安定IDを翻訳する。
カスタム名称・未定義IDは元の名称へフォールバック。ゲーム計算に翻訳処理はない。
既存の操作・引数・終了コードを維持し、languageとrequestを追加。

## BBS名前空間

bbs_accountsの主キーは(bbs_id, local_user_id)、内部player_idも一意。
既存プレイヤーは予約されたlocal名前空間へ移行。内部IDは変更しない。
Application.create_account / resolve_accountを信頼されたAdapterに提供。
同じ会員ID・表示名でも別BBSは独立した内部ID・資産。市場は同じ世界を参照。
bbs_idは将来の接続認証で確定する値。CLIに自由選択オプションは追加しない。
このAPI自体は認証ではなく、公開ネットワークへ直接公開してはいけない。

## 更新履歴と再送

登録・購入・売却・出発をoperation_historyに保存。BBS登録も履歴を保存。
売買等APIは任意のrequest_idキーワードを受け取り、既存呼び出しはそのまま有効。
キーは(season_id, actor, request_id)。操作と引数が同じ再送は保存済み結果を返す。
同じキーで内容が違えばREQUEST_CONFLICT。キー省略時は独立した新規操作として扱う。
成功した操作のみ、プレイヤーの前後状態・要求・結果・ゲーム時計と一緒に記録。
ゲーム状態と履歴は同一SQLiteトランザクション。失敗時は両方巻き戻す。
ローカルSQLiteのBEGIN IMMEDIATEで同時更新を直列化。履歴は自動削除しない。
ネットワーク認証、通信障害の実ネットワーク試験はPhase 5で統合。
クール終了処理は未実装であり、クール切替時の通信再送規約も後続課題。

## DB互換性

schema 1→2は追加テーブルのみ。旧ID・現金・積荷・船・現在地・航行期限・保存カタログを保持。
更新前にSQLite backup APIで <DB>.v1-backup-<unique>.db を保存し整合性確認。
移行のDDLとバージョン更新は同一トランザクション。失敗時はschema 1を保持。
既存カタログと異なる設定・未知schemaは従来どおり拒否する。
バックアップには他の更新を排除した状態の別読み取り接続を使用。
メモリDBは永続ファイルを持たないためバックアップを作らない。
ロールバック時はセッションを停止し、旧版と旧DBバックアップを別パスで起動する。
移行後のプレイ履歴は旧DBへ自動逆移行しない。
