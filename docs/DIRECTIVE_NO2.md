### 分類・正規化の実装条件

- Game Rules: 初期資金/船、商品・市場の初期/経済設定、船価/性能、航行/燃料、保険、投資/非公開開発上限、航路開拓/寄付、イベント条件/確率、破産/再出発、クール/進行条件。未実装領域は該当Phaseで追加。
- Site Settings: 表示言語、翻訳文言、端末文字コード/表示、BBS名、サイト接続先、ローカルログ先。安定した商品/船/惑星IDはゲーム側に残す。現行Catalog内の表示名は分類時に個別点検する。
- 実際の所持金・在庫・開発進捗等の可変状態と、その初期値・生成規則を区別する。取引ごとに設定ハッシュが変わる方式にはしない。
- Catalog.canonical()は既存DBの不一致検査と見積りに使用中なので、専用ハッシュのためにその意味を無断変更しない。保存済み要求結果・見積り互換への影響を評価する。
- 正規化方式を仕様化し、キー順、既定値の展開、未指定/null、整数・小数表現、非有限数、未知項目、重複キー、文字列の扱いを明記する。現行の整数限定項目は1.0を黙って許可せず、将来小数を受理する場合は数値同値の正規化を定義する。
- 配列は意味に応じて扱う。IDで識別され順序に意味がない集合は安定整列し、順序に意味がある配列は並べ替えない。JSONのsort_keysだけで完了としない。
- 有効設定へ反映されるルールを取りこぼさない。未知項目をどう扱うかは旧形式との互換を考慮し、共有ルールの検証不能を一致と扱わない。
- world_idは設定ハッシュそのものと区別して照合する。同じ設定の別世界を同一世界と見なさない。バックアップからの復元ではIDを保持し、独立した新世界として分岐するときのID発行方針を設計する。
- ハッシュは整合性の指標であり真正性の証明ではない。未決の署名方式・配布主体・プロトコルは固定しない。

### Phase 3の追加受入テスト

1. 同じ有効設定でハッシュ一致。JSONキー順と意味を持たない項目順の変更でも一致。
2. ゲームルールの変更でハッシュが変化。省略された既定値と明示値の扱いも固定テストにする。
3. 表示言語・BBS名・接続先・ログ先等のサイト設定を変えてもハッシュ不変（未実装設定は対応時に追加）。
4. 数値表現の扱い、重複キー、不正値、未対応バージョンの検証。別プロセス/Windows/FreeBSDで同一ハッシュ。
5. rules_version/config_schema_version/正規化方式を取得可能。DBスキーマ/アプリ版と混同しない。
6. ファイルを変更しても既存DBの有効設定とハッシュは変わらない。新規世界には新設定が適用される。
7. 既存の交易・航路・惑星・資産・航行期限・再送結果・BBS対応を維持。世界IDは再起動/移行再試行で変わらない。
8. 同じBBS内IDでもBBSまたは世界が異なれば識別を混同しない。既存単一BBSの呼出しを維持。
9. 非公開開発上限を将来ゲームルールへ追加した際、ハッシュに反映されるが公開DTOへ値を漏らさない。

## 3. 既存Phase 3C〜3Iへの追加条件

各Phaseで新しいパラメータを追加する際はCFG-01の共有ルールへ登録し、ハッシュ変更テストを同時に追加します。計算値を複数モジュールへ個別に直書きしません。
3C: 経済/生産/価格/乱数条件。3D: 投資/上限/資源。3E: 船購入条件。3F: 寄付/開通/工作船効果。3G: 抽選条件/確率/報酬。3H: 保険条件。3I: 再出発条件。
クール期間・進行条件はPhase 4で追加時にも同じ分類を適用します。暫定値と正式値は引き続き区別します。

## 4. Phase 5の追加タスク

| ID | 作業 |
|---|---|
| BBS-VERIFY-01 | 相手認証、world_id確認、正規マスター管理/取得/真正性検証。管理主体・配布・署名・プロトコルは詳細設計で確認 |
| BBS-VERIFY-02 | 自サイトと相手の有効設定を、それぞれ検証済み正規マスターと照合。相手の自己申告ハッシュだけで正常と判断しない |
| BBS-VERIFY-03 | 双方正常のみ参加許可。片方異常/双方異常/どちらか判定不能/マスター真正性不明は拒否し、共有更新を開始しない |
| BBS-VERIFY-04 | 管理者ログに分類、両サイトの版/ハッシュ、特定できる差分項目を記録。取得不能は未取得と記録し捏造しない。秘密値・非公開上限を公開ログへ出さない。設定の自動修正/上書きなし |
| BBS-VERIFY-05 | 接続成功/全拒否ケース、認証失敗、未検証マスター、偽の自己申告、途中障害、拒否時の共有更新ゼロを通信試験で検証 |

判定: 正常/正常=許可、正常/異常=REMOTE_CONFIG_MISMATCH、異常/正常=LOCAL_CONFIG_MISMATCH、異常/異常=BOTH_CONFIG_MISMATCH。正規参照が取得できない場合はREFERENCE_CONFIG_UNAVAILABLE、真正性や比較を検証できない場合はCONFIG_VERIFICATION_FAILEDを使う方針。いずれか判定不能ならローカル/リモートの異常と断定しません。具体的な原因の分類はPhase 5で詳細化します。
認証と設定検証を別要件として扱い、認証成功だけでは参加を許可しません。
