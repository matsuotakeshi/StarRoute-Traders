# 追加指示書No.8：差分と実装計画

2026-11-01 / 照合対象 v0.15.0。今回は仕様・計画の更新のみ。コード、設定、DB、配置は変更しない。
根拠は同日付のユーザー提供指示書No.8。以前の文書と競合する箇所はNo.8の確定事項を優先する。

## 確定事項と現状

| 項目 | 現状 | 追加対応 |
|---|---|---|
| 生成・配布・登録・Engine・API・BBS Clientの分離 | 外部生成器、基本検証、Engine、内部操作窓口あり | 配布・運用登録・通信API・BBS Clientを別責務で追加 |
| GitHub Private Repositoryによる配布 | 未実装 | Phase 4。完全パッケージの取得権限はマスター管理側だけ。EngineにGit/GitHub処理を入れない |
| スタンドアロン | ローカルEngine/DB/CLIは動作 | 共通パッケージの運用登録・有効化はPhase 4、BBS UIはPhase 5 |
| 途中参加・正式離脱 | 未実装 | Phase 5。対象ノードの別宇宙の進捗を引き継がず、BBSアカウント・サイト設定を維持 |
| 240×120 ASCII星図 | 未実装 | Phase 3。全体描画座標0..239/0..119、端末には船中心の部分表示 |
| 航行表示・制限 | 到着時刻/残秒、主要更新操作の係留条件あり | 現在位置、追従星図、ETA、ニュース、全操作の許可表を追加 |
| 惑星災害 | 相場イベントはあるが産業被害イベントは未実装 | 現在Lv低下、生産/供給への影響、確定ニュースを統合 |

GitHub障害では登録済みDBでゲームを継続する。Inter-BBSマスターとの通信断ではBBSの更新を停止し、許可されたキャッシュだけを表示する。一時通信断・同じ宇宙への再接続ではリセットしない。
正式な参加・離脱でも共有宇宙や他BBSを初期化しない。共有履歴・殿堂を不用意に削除しない。切替はバックアップと復旧可能な手順を伴う。
スタンドアロンのUIも秘密を表示しないが、ローカル管理者の内部ファイルアクセス防止までは保証しない。

## Phase 3の追加タスク

以下のIDは本書で追加する作業管理用ID。既存3E〜3Iを置き換えない。

| ID | 内容・受け入れ条件 |
|---|---|
| MAP-01 | 内部宇宙座標と描画座標を分離。240×120へ投影し、船中心・端末寸法に応じた範囲を境界内で切り出す。既存宇宙の座標/距離/航行費を変更しない |
| MAP-02 | 惑星はASCIIの*、船は+、停泊惑星と船は緑。正式英語名のON/OFF、日本語UIでも星図ラベルは英語。位置記号をラベルより優先。非公開座標・未発見航路を描かない |
| NAV-UI-01 | Engine側の航行情報から現在位置/ETAを得て表示。クライアントは到着を確定しない。旧保存データで不足する出発情報の互換方法を設計する |
| NAV-UI-02 | 航行中のゲームコマンドは原則ニュースのみ。売買・投資・寄付・船購入・新規航行等をEngine/操作窓口でも拒否。自動状態表示とプレイヤー操作を区別。ホストのログアウトは妨げない |
| NEWS-01 | 確定イベントIDに関連付けたニュースを保存。日英はメッセージキー/確定パラメータで表現し、再表示で再抽選しない。探索対象・非公開情報の漏出を防ぐ |
| DIS-01 | 惑星災害を航行海賊・既存の相場ショックと区別。現在Lvのみを対象とする暫定案を明記し、0未満を拒否。同じイベントの二重適用、保存再開での再抽選を防ぐ |
| DIS-02 | 被害時刻と生産期間の整合を保ち、生産/市場容量の減少を経済に接続。既存在庫が縮小後容量を超える場合の扱いを確認。全商品一律値上げや既存相場ショックとの二重計上を避ける |
| DIS-03 | 被害・関連状態・ニュースを原子的に保存。ニュースは実際の被害と一致。再投資での復興は基本案として扱い、正式な費用等は確認後に実装 |

産業Lvと工作船効果の端数・Lv0の生産を先に確認し、既存計画の3E船購入→3F航路寄付を維持する。
星図はMAP-01→02、航行表示はNAV-UI-01→02の順。ニュース基盤は惑星災害および3G船種イベントから再利用できるよう先行し、災害はDIS-01→02→03で追加する。
3H保険、3I破産も残件として維持する。有料ギルド通信とWHOは正式採用しない。

## Phase 4

- 独立したUniverse DistributionがPrivate Repositoryからパッケージを取得する。
- 形式/版/内容/完全性と信頼できる配布元を検証し、登録履歴・重複ID管理へ接続する。
- Git over SSHと読み取り専用Deploy Keyは基本案、署名付きマニフェストは推奨。最終方式を確定済みとしない。
- 登録と有効化を分離し、再取得/再登録で稼働中の動的状態を上書きしない。
- ローカルパッケージにも同じ登録・検証経路を用意し、GitHubや外部マスターを必須にしない。
- クール切替、旧世界の更新停止、ランキング・殿堂保全、バックアップ・復旧を実装する。

## Phase 5

- 集中型API、認証、信頼できる正規設定による自/接続先/双方の異常分類、公開情報だけの配信。
- 途中参加時の認証→整合性→対象宇宙確認→バックアップ→対象ノード切替→新規ゲーム登録。
- 正式離脱時の共有接続停止→バックアップ→ローカル新宇宙生成/登録/有効化。通信断を離脱扱いしない。
- 切替途中の障害、再参加時の既存マスターアカウントの扱い、処理中要求の結果確認を詳細設計する。
- BBS星図/ETA、共有ニュース、公開キャッシュ、日英UI、接続・配信ログ。
- 秘密パッケージやGitHubの取得資格情報を参加BBSへ配布しない。

## 確認事項・互換性・テスト

正式未決：配布認証/署名、パッケージ形式の今後の版、運用モード設定形式、管理UI、ビューポート寸法/更新周期、ラベル衝突/初期表示、停泊時の記号重なり、航行位置の補間/時間方式、航行中の表示設定変更、災害確率/産業/被害幅/最大Lvへの影響/復興式/経済効果。
最大Lvを不変にすることは基本案であり確定仕様へ昇格させない。既存のパッケージschema1、実時間ベースの保存航行は現行互換方式として保持する。
既存units方式の世界へLv災害を無断適用しない。新しい経済ルール/確率/方式は共有ルールとハッシュへ反映し、表示設定はサイト/ユーザー設定、被害・ニュース・現在Lvは動的状態に分離する。
