# Phase 3A — 船種・グレードのデータモデル (v0.3.0)

2026-11-01。今回の範囲は船定義、保存、定義検証、読み取りAPI、CLIの船情報表示。
Phase 3Bの航行方式変更、船の購入・交換、保険徴収、特殊イベントは実装していない。

## モデル

- ShipGrade: idとrank（大小関係を表す正整数）。正式グレード数・名称は未設定。
- ShipProfile: ship_id、ship_type、grade_id、normal_speed、max_warp_speed、purchase_price、insurance_premium、specification_status。
- 船種の内部IDはnormal（通常船）、armed_cruiser（仮装巡洋艦）、engineering（工作船）の3つのみ。
- 船種とgrade_idは独立。各船種で同じグレード定義を参照できる。
- 通常速度と最大ワープ速度は別の正整数モデル値。単位・倍率・航行時間の換算式は未確定。
- 価格・保険料は整数Crまたは未確定のnull。0を「未確定」の代わりに使わない。
- specification_statusはlegacy（旧定義）、provisional（暫定設定）、confirmed（設定作成者が確定と明示）。
- confirmedを受け付けることは、未決のゲーム数値が企画承認済みという意味ではない。配布する標準定義はlegacyのまま。
- grade_id、モデル速度・価格・保険料にはnullを保存できる。confirmedは全項目の指定を要求する。
- 型定義は凍結dataclass、返却DTOは独立した辞書。

## 互換性

既存format_version 1のカタログ・保存文字列は変更しない。
旧shipsテーブルと従来のcapacity/max_distance/speed、プレイヤーのship_idも保持。
スパロウを含む既存船の船種・正式グレードは未割当としてnullにする。これは第4の船種ではない。
元のspeedを新しい通常速度やワープ速度に無条件で流用しない。
当面の実航行計算は従来speed、積載計算は従来capacityを使う。
開始船や下位グレードを勝手に設定しない。既存の売買・出発・到着期限を変えない。
get_playerの応答は変えず、新しいApplication.get_ship(player_id)とCLIのshipコマンドでモデルを参照する。
これにより保存済みの再送結果もそのまま保持できる。

## カタログformat_version 2

新規設定ではship_grades配列（id, rank）と各ships行のprofileを明示する。
profileにはship_type、grade_id、normal_speed、max_warp_speed、purchase_price、insurance_premium、specification_statusを全て記載。
未確定項目はnull、試験値を置く場合はprovisionalとする。legacyは旧形式の読み込みにだけ使用。
既存のships基本属性も引き続き必要。新しいモデル値は実航行・自動課金へまだ適用しない。
設定例はtests/test_ships.py内のtest_catalog_data。test_low/test_highおよび全数値は試験専用で、正式な初期設定ではない。
旧DBへ異なるカタログを渡すと従来どおり拒否。新しい船定義への本番切替は、企画決定後に別の明示的カタログ移行として扱う。

## 確定済みの大小関係の検証

数値と比較対象が存在するときだけ比較し、未確定の値を推測して埋めない。
- 通常船の通常速度はグレードによらず同じ。
- 上位グレード通常船は積載量・最大ワープ速度・購入価格・保険料が大きい。
- 同グレード仮装巡洋艦は通常船と積載量・通常速度・最大ワープ速度が等しく、価格が高く保険料は低い。
- 同グレード工作船は通常船と積載量が等しく、通常速度・最大ワープ速度が低く、価格は高い。
- 工作船の保険料に未承認の比較条件は置かない。
比較対象の通常船がない未完成カタログは、単体属性を検証するが相対条件は判定しない。
この検証は定義上の整合性であり、新しい航行方式が実機で動作したことを意味しない。

## DB schema 3

ship_gradesとship_profilesを追加。既存テーブルは変更しない。
schema 1/2→3の前にSQLite backupで旧DBを保存。1の場合は既存基盤テーブルも同じトランザクション内で追加。
失敗時はDDL・バージョン更新を全て巻き戻し、旧DB形式を維持。
既存のID・残高・積荷・船・航行期限・言語・BBS対応表・履歴・要求ID・保存カタログを保持。
起動時に保存済み船モデルとカタログの一致を検証し、不一致を黙って上書きしない。
旧版へ戻す場合は旧版と旧DBを組にする。schema 3を旧版で開く運用はしない。

## 企画への確認事項（値はまだ確定していない）

1. グレード数・名称・順位、初回標準船とその1段階下の船。スパロウの正式な船種・グレードへの対応。
2. 各グレードの積載量・購入価格・通常速度・最大ワープ速度。型式名と同グレード内の型式の扱い。
3. 通常速度とワープ速度の単位・刻み・時間換算式、工作船の低速率。Phase 3B着手時に整理。
4. ワープ燃料費の計算式と見積り・確定方法。通常航行と係留の追加費用0 Crは確定済み。
5. 保険料の金額・課金タイミング・補償方式。特に工作船の保険料条件は未定。
6. 既存進行中航行への切替方針と新旧カタログの移行。今回の移行は既存期限をそのまま保持。

上記は確認待ちとして残す。試験用グレードや数値を実運用の正式仕様へ昇格させない。
船購入条件、投資ボーナス、イベント、破産清算は後続フェーズの確認事項を引き続き維持。
