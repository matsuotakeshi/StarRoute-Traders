## 3. Phase 3へ入る前の基盤整備（Phase 1・2の作り直しではない）

### A. 表示の独立

提案: presentation/locales/ja.json、en.jsonと名称ID辞書を用意。
CLI/Webはmessage_key + parameters、goods_id/planet_idから表示名を解決する。
Engineは表示文章や翻訳処理を呼ばず、金額を数値で返す。
現行DTOのnameは移行期間の互換フィールドとして扱い、将来の正規IDと混同しない。
言語設定はプレイヤー単位のPreference。言語変更によって設定以外の現金・積荷・市場・
乱数系列を変えない。UTF-8を基本とし、端末エンコーディングと文字幅はAdapter側で扱う。
英語完成をPhase 5へ割り当てても、新機能の日本語直書きを増やさない。

### B. 名前空間

提案: bbs_accounts(bbs_id, local_user_id, player_id)、UNIQUE(bbs_id, local_user_id)。
内部player_idは既存参照を維持し、外部IDの曖昧な文字列連結や表示名で照合しない。
異なるBBSの同一local_user_idを別の内部player_idへ割り当てる。
既存単体CLIプレイヤーは移行専用local名前空間へ対応付ける案。正確な識別子は移行時に決定。
bbs_idは信頼された接続元資格情報から確定する。利用者の自己申告で他BBSを選ばせない。
同一BBSアカウントがCLI/Door/Webを使う場合は同じ内部ID、別BBSなら別ID。
実在人物を追跡してBBS横断統合する機能は設けない。

### C. 更新履歴と重複排除

提案: Applicationの変更操作に認証済み主体・request_idを付加する。
処理済み要求と結果、資金/貨物/投資の更新を同一トランザクションで保存する。
再送は同じ結果を返し、同じrequest_idで異なる内容を送った場合は拒否する。
重複排除キーはクール・主体・request_id等で名前空間化し、認証境界と保存期間を設計する。
通信タイムアウト後に処理済みか不明でも、再送で資産を重複変動させない。
現ローカルCLIの呼出し互換を保つラッパーを用意する。ネットワーク通信はまだ追加しない。

### 投資データの分離

提案モデル: investment_records(season_id, player_id, target_kind, target_id, industry,
paid_credits, effect_units, bonus_policy_version, request_id)。
paid_creditsは実際の残高減算額、effect_unitsは開発進捗へ加算する量。二重計上しない。
惑星開発進捗と航路進捗は別の集約/テーブルに置く。
貢献ランキングが支払額・効果量のどちらを評価するかは未定で、計算を固定しない。
工作船効果がある場合、旧設計の「残必要額まで現金を受理」だけでは開通判定を表せないため、
閾値と効果量、余剰寄付の扱いを実装前に整理する。開通/報酬は原子的に一度だけ確定する。

### 非公開開発上限

提案: サーバ専用PlanetDevelopmentPolicyに上限/成長曲線を置き、公開DTOは許可項目のみ構築。
カタログ全体のJSON化や内部オブジェクトの自動シリアライズをクライアントAPIへ使わない。
上限は正規応答・失敗応答・イベント・CLI・Web・設定配信のいずれにも出さない。
上限近傍の鈍化による表現は未承認。独立産業上限か全体容量かも決めない。

### 船種イベント

- 仮装巡洋艦: 襲撃候補選定から除外し、別の討伐抽選を持つ。取得前に商品容積×数量を検査。
  満載なら取得なし。部分空きの場合の部分取得/全量不成立は企画確認。
- 工作船: 抽選資格を「係留操作回数」に依存させない。
  提案は経過時間のeligible tickと船/惑星/クール/抽選IDの一意記録による再抽選防止。
  係留と再接続を繰り返しても同じ時間帯の報酬を増やさない。
  第1次産業/資源を条件にしつつ、低開発・未開拓を確率0に固定しない。
  発見物の貨物化・価値は未定で、仮装巡洋艦の貨物仕様を無断で流用しない。

### 破産の実装前確認（明示的な確認が必要）

再出発資金、清算対象（貨物/現金/その他資産）、再出発惑星、探索/開拓/成績の保持範囲、
履歴の保存/表示、移動・資金調整目的の悪用対策を企画へまとめて確認する。
初回開始船より1グレード下、初回より少額という確定条件を検証する。
破産直前の所有船を基準にしない。任意破産と難破保険救済は別操作・別台帳種別にする。

## 7. 受け入れ基準とテスト割当

未実装の基準は「予定」であり、現在の40テストで検証済みとは扱わない。
各段階の完成時に既存テストを回帰実行し、以下を実テストとして追加する。

| 指示書の基準 | テスト内容 | 段階 |
|---|---|---|
| 1 | 通常船の複数グレードで通常時間同一、積載/最大ワープ速度上昇 | 3A/B |
| 2 | 同等グレードで工作船の通常/最大ワープ双方が遅い | 3A/B |
| 3 | 船種/惑星/開発度/時間の組合せで通常追加費・係留費とも0 | 3B |
| 4 | ワープ速度増加時の有料見積りと確定額、資金不足時の全ロールバック | 3B |
| 5 | 仮装巡洋艦に襲撃なし。seed固定の討伐抽選で貨物獲得 | 3G |
| 6 | 空き0・容積2・容量境界で戦利品超過なし | 3G |
| 7 | 同額投資で工作船の効果のみ増加、支払額・残高減算は同額 | 3F |
| 8 | 資源/第1次産業が抽選へ反映、低開発でも発見可能。同tick再操作/再接続で重複なし | 3G |
| 9 | 開発条件の前後で船購入可否が変わり、全プレイヤーから見える | 3E |
| 10 | API/CLI/Web/エラー/シリアライズから非公開上限を取得不可 | 3D、5で通信検証 |
| 11 | 高級船/低級船いずれの破産でも初回標準船の1グレード下・初回より少額 | 3I |
| 12 | BBS A/Bの同じ会員ID・同じ表示名が別資産、両者の投資/売買は共通世界に反映 | 基盤、5で通信検証 |
| 13 | 同一状態/seed/時計のja/en操作結果が同じ。言語設定以外の保存値は不変 | 基盤、5で全翻訳検証 |

追加検証: 同時投資/最後の寄付の競合、同じ要求の再送、応答喪失後の再送、
同じ要求IDの内容改変、資産と効果量の二重加算禁止、開通報酬の一回性、
DB移行の保存/ロールバック、クール切替時の更新競合、殿堂の上位3名と永続性。
船価格/保険料の大小関係、3系統以外の誤追加拒否も定義検証に加える。
乱数イベントはseed/clock注入で再現可能にし、未決の数値は試験用fixtureに限定する。

## 8. 未決事項と着手時の確認

| 判断項目 | 確認時期 |
|---|---|
| グレード数・型式・開始船とその1つ下、価格/容量/速度 | 3A着手時 |
| ワープ段階・燃料費式・時間、工作船低速率 | 3B着手時 |
| 開発上限方式・成長曲線・投資効率、資源特性の定義 | 3D着手時 |
| 各産業の品目/生産/相場効果、船購入の産業条件、船交換処理 | 3C〜Eの接続前 |
| 工作船ボーナス率、開通閾値/余剰寄付、ジャックポット評価と配分 | 3F着手時 |
| 海賊討伐/鉱物発見の確率・価値・取得/容量処理 | 3G着手時 |
| 船種別保険料・補償率・救済条件 | 3H着手時 |
| 破産後資金/清算/位置/進捗/履歴/悪用対策 | 3I実装前に必ず確認 |
