# StarRoute Traders 追加開発指示書 No.9
## FreeBSD Ports化・pkg配布・安全な更新機構・ゲーム時間調整

**作成日：2026年11月2日**  
**開発基準：v0.18.0以降の最新開発成果物**  
**対象：StarRoute Traders / FreeBSD 15.1 amd64**  
**優先度：高**

---

## 1. 開発目的

StarRoute Tradersの更新作業を簡素化するため、FreeBSD Portsに準拠したパッケージ管理機構を構築してください。

現在は開発成果物をFreeBSDへ手動でコピー・配置する必要があり、更新のたびに一定の作業時間が発生しています。

今回の目標は、以下を実現することです。

1. StarRoute TradersをプライベートPortとして管理する。
2. スタンドアロン、マスターサーバ、BBSクライアントを用途別にパッケージ化する。
3. poudriereを使用してpkgパッケージを生成する。
4. 独自pkgリポジトリを構築する。
5. `pkg upgrade`による更新を可能にする。
6. 更新時にゲームデータ・設定・認証情報を維持する。
7. 更新失敗時に旧バージョンへ復旧できるようにする。
8. Liner notesとのDoor連携を維持する。

また、最近決定した航行時間と世界イベント周期の変更も、次期リリースに反映してください。

**既存の本番環境は変更せず、独立した検証環境で実装・動作検証まで完了してください。**

## 2. 開発基準の確認

StarRoute Traders v0.18.0では、Phase 1〜5が完了しています。

その後、BBS画面が以下の構成へ改修されています。

- 左側にASCII星図
- 右側に縦型メニュー
- 数字・1文字キーによる操作
- 対話型の商品売買
- Telnet/PTY/NAWS対応
- 日本語・英語表示
- Inter-BBS対応

作業開始時には、実際の最新ソース・バージョン・変更履歴を確認してください。

古いv0.18.0のアーカイブをそのままパッケージ化し、後から追加されたBBS UI改修を失わないようにしてください。

既存の430件のテストは最低限維持します。UI改修後に追加されたテストがあれば、それらも対象に含めてください。

## 3. Ports構成【必須】

プライベートPortsツリーに以下のPortを作成してください。

| Port | 役割 |
|---|---|
| `games/starroute-traders` | スタンドアロン版・共通ゲーム実行基盤 |
| `games/starroute-traders-master` | Inter-BBSマスターサーバ |
| `games/starroute-traders-client` | BBS Doorクライアント |

### 3.1 パッケージ分離

マスターサーバ用のコード、ゲームエンジン、BBSクライアントを適切に分離してください。

既存の配布成果物に含まれる`bbs-client.zip`の配布境界を維持すること。

**BBSクライアント用パッケージに、宇宙DB、隠し開発上限、生成シード、マスター認証鍵、マスター専用管理ツールを含めてはいけません。**

共通Pythonモジュールの扱いは、依存関係やインストールファイルの重複を避けられるように設計してください。

パッケージ構成の詳細は既存コードを確認して決定して構いませんが、最終的に用途別のpkgを生成できることを必須とします。

### 3.2 Portの基本ファイル

各PortにはFreeBSD Portsの規約に従い、必要に応じて以下を用意してください。

- Makefile
- distinfo
- pkg-descr
- pkg-plist
- files/
- pkg-message
- rc.dスクリプト

既存ソースの配布アーカイブから再現可能なパッケージを構築できるようにします。

ソースアーカイブは特定バージョンに固定し、SHA-256で検証してください。

ソースが現在ローカルにしか存在しない場合は、ローカルdistfileによるビルド方式を整備してください。

実在しないGitHubリリースURLを仮定して実装しないこと。

## 4. FreeBSD標準ディレクトリ構成

以下を基本案とします。

| 用途 | 配置先 |
|---|---|
| 実行コマンド | `/usr/local/bin/` |
| Pythonプログラム | `/usr/local/libexec/starroute-traders/` 等 |
| 設定ファイル | `/usr/local/etc/starroute-traders/` |
| 宇宙DB・ゲーム状態 | `/var/db/starroute-traders/` |
| ログ | `/var/log/starroute-traders/` |
| rc.d | `/usr/local/etc/rc.d/` |
| ドキュメント | `/usr/local/share/doc/starroute-traders/` |

Pythonモジュールの実際の配置はPortsのPythonフレームワークに合わせて調整して構いません。

### 4.1 最重要原則

**プログラム、設定、ゲームデータを分離してください。**

pkgが更新するのは、原則としてプログラム本体と配布用のサンプル設定です。

以下はpkgによる通常更新・削除の対象にしてはいけません。

- プレイヤーDB
- クール情報
- 宇宙データ
- ランキング・殿堂
- 認証鍵・証明書
- 運用ログ
- 管理者が編集した設定

### 4.2 設定ファイル

設定ファイルは`.sample`形式で配布し、Portsの`@sample`を利用してください。

既存の設定内容を更新時に上書きしないこと。

新しい設定項目が増えた場合は、互換性を保ちつつ管理者が変更点を確認できるようにしてください。

## 5. Python実行環境

StarRoute TradersはPython 3.10以上を想定しています。

FreeBSD Portsの`USES=python`を利用し、サポートするPythonバージョンと依存関係を明示してください。

- Pythonの実行パスを固定しない。
- 必要な実行時依存を適切に登録する。
- 不要な依存ライブラリを増やさない。
- FreeBSD 15.1 amd64で検証する。
- Windows側の開発・テストを維持する。

Python標準ライブラリだけで実装されている部分に、不必要な外部フレームワークを導入しないこと。

## 6. マスターサーバのサービス管理

マスターサーバ用Portには、FreeBSDのrc.dスクリプトを用意してください。

Portsの`USE_RC_SUBR`を使用することを基本とします。

必要な管理操作：

- start
- stop
- restart
- status

以下の条件を守ってください。

1. サービスは既定で自動起動しない。
2. インストール直後にマスターサーバを勝手に起動しない。
3. 更新時に稼働サービスを無断停止しない。
4. 非root権限での実行を基本とする。
5. 秘密鍵・ゲームDBへのアクセス権限を適切に制限する。
6. PID管理・ログ管理・異常終了時の動作を整備する。

スタンドアロン版およびDoorクライアントについては、不要な常駐サービスを作らないでください。

## 7. 独自pkgリポジトリ【必須】

### 7.1 最終目標

FreeBSDのpkgコマンドで以下の操作ができるようにします。

- pkg install
- pkg upgrade
- pkg info
- pkg delete

公式FreeBSD Portsへの登録は今回の対象外です。

プライベートPortsおよび独自pkgリポジトリで運用してください。

### 7.2 poudriere

poudriereによるパッケージ構築を実装・検証してください。

- FreeBSD 15.1 amd64を対象にする。
- 隔離されたビルド環境を使用する。
- 依存パッケージを解決する。
- pkg-plistを検証する。
- ビルドログを保存する。
- インストール可能なpkgを生成する。

既存のFreeBSD本番環境へpoudriereの設定変更を直接行わず、検証用環境で実施してください。

### 7.3 リポジトリ

まずローカルの`file://`方式で独自pkgリポジトリを構築してください。

その後、必要ならHTTPS等による配布へ拡張できる構造にします。

- 公式FreeBSD pkgリポジトリとの共存を考慮する。
- StarRoute Traders用のリポジトリを明確に区別する。
- 不明なパッケージで公式パッケージを置き換えない。
- 本番向け配布ではリポジトリ署名・検証を設計する。
- リポジトリを無断でインターネットへ公開しない。

### 7.4 GitHubとの分離

既存のGitHub Private Repositoryは、Inter-BBS用の宇宙マスターデータ配布に利用するものです。

**ゲームプログラムのpkgリポジトリと、宇宙マスターデータのGitHubリポジトリを混同しないでください。**

プログラムの更新によって、稼働中の宇宙が自動的に切り替わる設計は禁止します。

## 8. 更新・ロールバック機構【最重要】

今回のPorts化で最も重要な目的です。

### 8.1 通常更新

通常の更新操作で、プログラムを新しいバージョンへ置き換えられるようにしてください。

必要な場合は、サービス停止、バックアップ、パッケージ更新、DB移行、再起動を行います。

ただし、これらをpkgのインストールスクリプトから無条件に自動実行してはいけません。

### 8.2 DBマイグレーション

DBのスキーマ更新が必要な場合は、別の明示的な管理コマンドとして実装します。

条件：

- 更新前にバックアップ
- スキーマバージョン確認
- 互換性チェック
- 失敗時の安全停止
- integrity_check
- 外部キー整合性確認
- 更新履歴の記録

既存の宇宙やプレイヤーデータを無断初期化しないでください。

### 8.3 ロールバック

更新失敗時には、保存してある旧バージョンのpkgとDBバックアップから復旧できるようにします。

ただし、**古いpkgを再インストールするだけで、新しいスキーマのDBが必ず利用できるとは限りません。**

そのため、プログラムとDBのバージョン整合性を確認し、必要な場合は両方を対応する時点へ復元する手順を用意してください。

ロールバック可能性を検証していない状態で、復旧可能と報告してはいけません。

### 8.4 アンインストール

`pkg delete`でプログラムを削除した場合も、ゲームDBや殿堂記録などの運用データは保持してください。

データの完全削除は、管理者が別途明示的に実行する操作とします。

## 9. 最近決定したゲーム時間の変更

Ports化とは独立したゲームバランス変更として実装してください。

パッケージ化によって、これらの設定を変更・更新しやすくすることも目的とします。

### 9.1 惑星間航行時間【基本方針確定】

GFTのゲームテンポに合わせ、惑星間航行は現実時間で数時間単位とします。

既存の数分で到着する試遊向け設定から、長時間航行を前提とした設定へ変更してください。

想定する時間帯：

| 距離 | 通常航行の暫定目安 |
|---|---|
| 近距離 | 2〜4時間 |
| 中距離 | 6〜12時間 |
| 長距離 | 12〜24時間 |

これは正式な距離別所要時間表ではなく、調整用の参考値です。

ワープによる短縮率や燃料費についても、既存ゲームルールを維持しながら設定可能にしてください。

### 9.2 ログアウト中の航行【確定】

- ログアウトしても航行は中断しない。
- Doorを終了しても航行は続く。
- 到着判定にはサーバ側の実時刻を使用する。
- 再ログイン時に現在位置または到着状態を正しく表示する。
- BBSへ長時間接続し続ける必要はない。

スタンドアロンではローカルGame Engine、Inter-BBSでは集中型マスターサーバが時刻・航行状態の正となります。

### 9.3 ゲーム世界の継続進行

プレイヤーがログアウト中でも、次の処理は進行します。

- 商品生産・在庫補充
- 市場価格の更新
- 惑星災害などの世界イベント
- ニュース生成
- 他プレイヤーによる投資・航路開拓
- 航行の進捗

サーバ再起動後にも、未処理の時間経過を正しく反映してください。

## 10. 世界イベント周期【確定】

世界イベントの判定周期を、従来の暫定300秒から次の値に変更します。

**イベント判定周期：7,200秒（2時間）**

重要なのは、2時間ごとに必ず事件を発生させないことです。

### 10.1 発生判定

2時間ごとに宇宙全体で低確率のイベント発生判定を実施します。

- 抽選に外れた場合は何も発生しない。
- 抽選に当たった場合にイベント種類と対象惑星を決定する。
- 全48惑星で独立した高頻度の災害抽選を行わない。
- 実際の発生確率は設定可能とする。
- 発生確率の具体値は未確定であり、正式仕様として固定しない。

対象イベントには以下を含めます。

- 海賊の惑星襲来
- サイクロン
- 工場事故

既存の災害による産業開発レベル低下、生産・供給能力変化、相場変動、ニュース生成の仕組みを維持してください。

### 10.2 時間経過と重複防止

イベント判定には、現実時刻に基づく時間枠と、処理済み判定を識別できる情報を使用してください。

- 同じ2時間枠を二重処理しない。
- サーバ再起動後に未処理の時間枠を判定する。
- 再ログインを契機として同じ事件を重複発生させない。
- 判定結果とニュースを整合させる。
- 過去の判定時刻を適切に記録する。

生産・市場価格の更新周期は、世界イベント周期から独立させます。

なお、航行中に発生する個別の海賊襲撃や磁気嵐などは、既存の航行イベントです。これらを一律に2時間周期へ変更する必要はありません。

## 12. 実動作検証

次のシナリオを実施してください。

### A. 新規インストール

クリーンなFreeBSD検証環境で、pkgからStarRoute Tradersをインストールします。

必要な初期設定を行い、スタンドアロンでゲームを起動できることを確認します。

### B. アップグレード

旧バージョンをインストールし、プレイヤーを登録して交易・投資を実行します。

その後、新しいpkgへアップグレードし、以下を確認します。

- プレイヤー資産が残る。
- 宇宙の座標・産出商品が変わらない。
- 産業開発状態が残る。
- クールと殿堂が残る。
- Liner notesから再びゲームを起動できる。

### C. 障害復旧

更新中の異常終了やDB移行失敗を再現し、バックアップと旧pkgから復旧できることを確認します。

### D. 長時間航行

試験用の時刻制御を利用し、数時間の航行とログアウト・再ログインを再現します。

実際に数時間待つ必要はありませんが、時間計算の正確性を確認してください。

### E. 世界イベント

2時間周期を時刻制御によって再現し、イベント不発・イベント発生・サーバ再起動・未処理時間枠の回収を検証します。

Port名の候補：

`net/linernotes`

ただし、今回の必須完成範囲はStarRoute Tradersとします。

Liner notesのPorts化は、既存のBBSデータ、ユーザー情報、汎用Door Manager、Telnetサービスの保護が必要になるため、別工程として扱ってください。

今回の開発では、将来Liner notes本体をpkg管理しても、StarRoute Tradersクライアントとの連携が失われない構成を整えてください。

Door設定への自動追記や、本番BBS設定の無断変更は禁止します。

## 16. 開発担当への最終指示

**今回の最大の目的は、StarRoute Tradersの更新にかかる手作業を減らすことです。**

開発成果物を手動でコピーし直す運用から、FreeBSDのpkgで安全にインストール・更新できる運用へ移行してください。

まずプライベートPortsを作成し、次にpoudriereでpkgを構築し、独自pkgリポジトリを整備してください。

将来のバージョンアップでは、更新用pkgを作成して登録すれば、管理者が簡単にアップグレードできる状態を目指します。

さらに、今回確定した以下の変更を反映してください。

- 惑星間航行は現実時間で数時間単位
- ログアウト中もゲーム世界は進行
- 世界イベントは2時間ごとに低確率で抽選
- 生産・相場更新と災害イベントは独立
