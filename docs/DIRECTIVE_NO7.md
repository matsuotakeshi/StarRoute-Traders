# 追加指示書No.7：外部生成器・産業Lv・宇宙パッケージ

v0.15.0 / 2026-11-01。No.7の確定仕様を優先し、Phase 3の差分を実装。
No.6の「マスターが生成を担当」は、マスター管理者が外部ツールで生成し、別の取り込み機構に渡す構成へ更新する。

## 責務と今回の実装範囲

| 機能 | 今回の状態 | 配置・責務 |
|---|---|---|
| Universe Generator | 外部ツールとして分離 | オフライン生成と出力前検証。DB・Engine・Application・BBSクライアントを含まない単独ZIPを用意 |
| Package validation | 基本検証と変換器を追加 | 別プロセスで形式・完全性・内容を検証。DBに触らず、検証結果を記録 |
| Universe registration / activation | 未実装 | 重複Universe ID管理、登録履歴、有効化、クール切替と復旧はPhase 4 |
| Master Universe Distribution API | 未実装 | No.6の公開投影を維持。通信・認証・BBS配信・キャッシュはPhase 5 |

生成済みと検証済みを今回区別する。検証成功でも登録済み/有効化済みにはしない。
生の宇宙パッケージをBBSへ配布しない。ゲーム実行中に生成器を呼ばない。

## 産業Lv

新しい生成版 `srt-universe-levels-v2` は、各惑星の4産業を独立して生成する。

```
MaximumLevel >= 1
InitialLevel >= 0
InitialLevel <= MaximumLevel
```

`examples/industry-levels-trial.json` で産業ごとに最大Lvの生成範囲を指定する。
試遊値は各産業1〜5だが、正式な全体上限ではない。設定を変更できる。
モード `independent_levels_v1` は暫定的に整数一様分布とし、初期値は0〜最大Lvから選ぶ。
境界試験/試遊用に、すべて初期0の `zero_v1` と初期＝最大の `maximum_v1` も選べる。
分布・相関・産出品との関連付けは正式決定していない。現在は惑星ID/産業/用途で分けた決定的な乱数を使用する。
惑星の名前の意味から産業特性を決めない。

従来の開発進捗は `linear_units_v1` のまま維持する。
新世界は `linear_levels_v1` とし、DBの進捗欄を整数Lvとして扱う。旧セーブをLvへ自動変換しない。
新方式では最大0を設定読み込み時にも拒否する。旧方式の既存値は互換性のため維持する。
開始時は生成された初期Lvを使い、CLIでは「現在Lv」、BBS向け内部窓口では `level` のみを返す。
最大Lv・シード・生成入力は非公開。公開投影・固定公開ハッシュへ最大Lvを混ぜない。

投資は既存のマスター側検証/トランザクションを再利用し、最大を超える要求は全額不成立・無課金とする。
これは既存の暫定挙動を維持したもので、上限時の受付/費用/メッセージの正式仕様ではない。
試遊では従来のcredits_per_unitを1Lvあたりの費用として再利用し、工作船の既存効果計算も維持。
費用/レベル効果/端数の正式調整は未決定。Lv0でも既存の基礎生産・市場を維持し、無断で停止させない。
Lv0時の詳細効果は確認事項とし、ECON-05の期間別能力反映を継続する。

## 外部ツールの分離

生成アルゴリズムは `srt_universe_generator` へ移動した。
単独ZIPはこの外部ツールと純粋なデータ検証モジュール/マスター/試遊設定を含む。
共有検証コードは従来の `starroute` 名前空間を使うが、Game Engine、Application、Repository、SQLite処理を同梱しない。
Python標準ライブラリのみで動作する。ゲーム本体の起動/インストールは不要。
検証と型の重複を避けるため、ゲーム側と同じデータ検証コードを再利用する。

ゲーム側の `Catalog` 読み込みでは生成アルゴリズムを呼ばなくなった。
保存済みデータの形式、座標、接続性、設定との対応、産業範囲、定義ハッシュを検証する。
外部生成器のimportを禁止した環境でも、パッケージ検証・新規試験DB・保存済みDBの再読込が可能であることをテストする。

旧 `starroute.universe.generate` と `python -m starroute.generate` は明示的な旧デモ起動用の互換入口。
実行時だけ外部ツールへ委譲し、ゲーム側の読み込み経路からは呼ばない。ゲーム用配布の必須依存にはしない。
旧v1アルゴリズムを外部側に残し、従来の再現デモを継続する。

## パッケージ形式と変換

JSON、`format: starroute-universe-package`、`schema_version: 1`。
内部CatalogやSQL行をそのままパッケージ本体にはしない。

| 区分 | 内容 |
|---|---|
| metadata | Universe ID、Generator Version、Game Rules Version、生成日時、Universe Data Version |
| reproduction | 非公開シード、生成パラメータ、産業Lv方針、版付き生成入力 |
| rules | 商品/船/経済/投資等の共通定義 |
| world | 初期地点、48惑星、航路、航行表、イベント対象 |
| world.planets | 固定ID、日英正式名、座標、産業ごとのinitial_level/maximum_level、産出/輸入/市場/資源 |
| integrity | 正規化したパッケージ全体のSHA-256 |

再現用入力には、形式名 `srt-catalog-v2` とレシピ版を明記して従来テンプレートを保持する。
これは初期版の再現用入力であり、外部の惑星データ仕様を内部DBの構造へ固定するものではない。
`to_catalog` が版ごとの外部形式から内部構造へ変換する。将来の形式変更は明示的な新スキーマ/変換器で扱う。

生成器の出力前と、独立した検証ツールの双方で以下を検証する。

- 形式/スキーマ/レシピ版、必須項目、未知項目、生成日時、完全性ハッシュ。
- 48個のIDが重複なく揃い、日本語名/英語名が正式マスターと一致する。
- 48×4＝192組すべての整数Lv範囲。欠落、最大0、負値、初期超過、浮動小数、真偽値を拒否。
- 座標・商品・市場・産出・航路・開発/航行ルールの整合性。
- 固定宇宙定義ハッシュと、変換後にエンジンへ渡すデータの一致。

検証ツールは32MiBを超える入力を拒否する。これは実装上の受付上限で、正式な宇宙規模ではない。
未知版や不正データを補修/上書きしない。検証結果はvalidatedまたはrejectedとして出力し、任意の専用ログへ保存する。
登録DBはまだ存在しないため、重複Universe IDの登録判定・永続的なインポート履歴はPhase 4で実装する。

## 完全性・真正性・秘密情報

パッケージと検証ログはFreeBSDで0600により新規作成し、既存ファイルを上書きしない。
Windowsでは保存先のACLも管理する。公開Web配下へ配置せず、マスター管理者専用の保管領域を使う。
パッケージ、旧生成JSON、マスターDB、再現用シードをBBSへ送らない。
SHA-256は破損検出であり、署名/認証ではない。検証結果には `authenticity: not_verified` を明示する。
正式な配布経路・署名・認証はPhase 4/5の詳細設計待ち。
ハッシュを再計算できる相手の改変に対して真正性を保証したとは扱わない。

実行時はシードからの再生成を行わないため、検証は生成アルゴリズムの再実行による照合ではなく、
保存内容・ルール範囲・参照関係・チェックサムの照合となる。厳密な再現調査は外部生成器で行う。
従来v1セーブの固定定義ハッシュを維持する。旧形式には再現メタデータ用チェックサムがない場合がある。
新しく出すv1互換データとv2データにはメタデータ用チェックサムを追加する。いずれも真正性を保証する署名ではない。

BBS向け内部窓口に対しては、許可された現在Lvと公開定義だけを検証対象にする。
同じ公開定義/共通ルールでも異なる非公開最大Lvが成立するテストにより、公開定義が最大Lvを直接符号化していないことを確認する。
想定は「BBS管理者が許可された応答やキャッシュを読めるが、マスターの秘密ファイル/シードにはアクセスできない」範囲。
これは全ての推測攻撃に対する数学的保証ではない。弱いシードの推測、反復投資からの推測、通信認証等の評価は後続設計で扱う。
実ネットワーク配信とBBSキャッシュ自体はまだ未実装。

## 識別情報の分離

| 情報 | 管理 |
|---|---|
| Game Rules Hash | 共有ルール/生成条件を照合。初期Lv/最大Lvという個別の生成結果は固定宇宙へ分離 |
| Universe ID | 宇宙インスタンスのUUID |
| Universe Data Version | 完全な固定宇宙定義のSHA-256。マスター専用 |
| Public Data Version | 公開投影版1と、閲覧範囲ごとの公開定義ハッシュ。完全定義とは別 |
| Dynamic State Version | 現在在庫/価格/進捗等の更新管理。配信向け版番号/差分管理の方式はPhase 5で決定 |

ゲームルール版は `phase3-industry-levels-1`、設定スキーマ9へ更新。
旧世界のプレイ条件は変更しないが、照合用ハッシュの版は更新される。過去台帳の記録済みハッシュは書き換えない。
個別Lv、現在市場、現在進捗を共有ルールの不一致として扱わない。
DBスキーマは9のまま。旧世界の状態・定義を新レベル方式へ置換しない。

## 実行例

外部ツールのZIPを管理者専用ディレクトリへ展開して実行する。

```
python -m srt_universe_generator --template examples/industry-effects-trial.json --parameters examples/universe-generator-trial.json --levels examples/industry-levels-trial.json --seed PRIVATE-SEED --output private-universe.json
```

別の検証工程（マスター側の管理環境）：

```
python -m starroute.package_check --input private-universe.json --report validation-report.json
```

このコマンドは登録・有効化・現在の世界の置換をしない。
生成パッケージを既存CLIの `--config` に直接指定する機能も追加しない。
Phase 4で、登録・承認/有効化・クール切替を独立して実装する。
試験専用DBでの生成→検証→Lv0投資→保存再開：`python scripts/package_demo.py`。
全試験：`python -m unittest discover -s tests -v`。
